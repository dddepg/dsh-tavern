## 当前行为，避免误解

每次首次请求模型生成 MVU 更新，都会携带完整当前变量和启用的更新规则。后台请求会移除上一轮非固定任务上下文，保留固定前缀，再加入本轮材料；不是每轮累积一份旧规则，也不会删除玩家历史或存档。

现有更新是增量 operations。工具失败可以修正重试，成功后结束本轮变量提交；这与多个 Skill 分阶段完成多次成功更新不同。已有 pendingSubmission 或 prepared 结果的恢复，不一定重新调用模型。

## 用户提出的方向：规则做成 Skill

把一整块更新规则拆成多个可按需读取的 Skill，每个负责一小部分变量。每轮先提供简短目录，再读取相关规则；变量值也应随规则一起按需读取，否则只缩小规则仍会全量注入变量。

可探索按业务领域或动作分组，而非机械地每几个变量一组：

- 人物关系：好感、信任、关系状态。
- 企业交易：资金、资产、负债。
- 生产销售：库存、产能、收入、成本。
- 时间推进：到期事件、周期收支。

每个 Skill 可描述适用情形、覆盖变量路径、规则正文及必要依赖。先保留少量公共约束和全局状态；相关 Skill 尽量批量读取，缺少信息时再补读。

需要解决的核心问题是跨领域依赖。例如买工厂同时涉及扣款、资产登记与产能，不能只加载资产规则就漏掉扣钱。目录本身也不能随着对象数量无限增长：领域规则与具体企业、人物的数据索引应分开考虑。

这里的 Skill 是按需读取规则的设计概念，是否复用现有 Skill 工具和文件格式、由谁拆分与维护，均未决定。

## 延伸讨论：一轮可以多次更新

用户提出，一轮不必只有一次变量更新，可以由多个 Skill 分别处理相关部分。

曾讨论“多次更新工作副本，最终统一校验保存”：后续 Skill 可以看到前面修改，全部完成后提交；中断时保留工作进度，恢复时检查剧情版本，避免钱已扣但资产没增加等半完成状态。

**这只是备选方案，用户认为目前太复杂，并未决定采用。** 是否需要工作副本、分阶段保存、依赖调度与恢复机制，留待重新评估。简单回合应能一次结束，不能为了拆分而强制多轮模型调用，增加延迟与成本。

## 保留的约束

- 完整变量和历史仍在存档中；未披露不等于不存在，不因模型未读取而删除或重置。
- 需要完整历史的兼容脚本仍可读取，不能统一硬截为最近 20 或 100 条。
- 局部更新保留完整状态校验、跨领域一致性以及过期任务保护。
- 旧人物卡保留全量兼容路径；长规则自动分组应先预览并检查遗漏，避免直接截断或静默改写原规则。
- 稳定规则放入固定前缀可能改善缓存，但不会消除上下文容量问题，也不保证实际命中缓存。

## 以后恢复工作时的最小验证

先补齐一次真实模型请求的输入、输出、缓存 token、首个增量等待、总生成时间和工具执行时间。确认最终请求中是否重复注入变量或规则。

随后只选一个领域做小实验：同一份正文和结算前状态，比较全量方式与按需读取方式的输入量、总耗时、工具往返、遗漏更新和最终状态。场景至少包含一个简单回合、一次跨领域交易和一次时间推进。先验证是否值得做，再决定是否引入多次成功更新；本备忘不要求一次性建成完整框架。
