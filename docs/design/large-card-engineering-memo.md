# 大型人物卡机制工程化备忘

> 状态：阶段性产品判断，不是新格式或实施规格。

## 背景

社区通过 EJS、世界书、MVU 变量及人物卡脚本，已经逐步拼出了相当完整的游戏机制：世界书按情境选择资料，MVU 保存结构化状态并结算更新，EJS 与脚本提供动态逻辑。大型人物卡面临的重点因此不一定是“现有机制做不到”，而是资料和规则规模超过模型注意力后，如何分层加载、检索和执行。

曾考虑为人物卡提供专属插件或工具，让卡片携带自己的后台结算程序。它可能把游戏逻辑封装得更明确，但目前没有证明其表达能力超出现有机制；若引入新格式或安装体系，还会增加创作、迁移、兼容和维护成本。

## 当前判断

现阶段不创建人物卡专属插件格式，也不要求用户迁移到一套新机制。优先沿用社区熟悉的 EJS、世界书、MVU 和 Helper 脚本，研究怎样把既有能力组合得更工程化、更容易创作、运行和调试。

## 结算策略：按卡片转换状态分流

普通卡与转换卡采用不同的上下文供给策略，后台仍使用同一个结算 Agent 和同一条变量提交链路：

| 卡片状态 | 结算上下文 |
| --- | --- |
| 未转换卡 | 保持当前方式：向结算 Agent 提供现有变量快照、变量结构和整份更新规则。 |
| 已转换卡 | 每轮只提供精简变量目录，不注入整份更新规则；结算 Agent 通过变量检索工具自主查找所需变量、当前值、定义及关联更新规则。 |

转换必须产出可检索结构：稳定变量路径/ID、精简目录、可单独读取的更新规则，以及规则与变量的关联。自主检索结果只是注意力起点，不是更新白名单；Agent 发现候选不足时仍可扩展检索。最终仍调用现有 `mvu_submit_update`，由现有 MVU Runtime 和 Host 校验、执行与提交。

这样普通卡无需迁移即可维持现状；转换卡获得渐进式加载，省去每轮重复传送整份更新规则。目录本身必须轻量，转换还需验证规则和变量覆盖率。额外工具往返可能增加延迟，因此整体收益需要用真实大卡实测。

## 后续评估原则

- 先拿真实大型卡验证：变量目录的体量、检索召回是否足够、状态与规则依赖是否可扩展，以及上下文 Token 的实际节省。
- 按明确的转换状态选择结算策略；不能把未转换卡误当成具有完整目录，也不能因未转换而阻断现有结算。
- 先复用现有机制与接口；不要仅为“插件化”新增并行运行时或新卡片格式。
- 不单独创建规则筛选 Agent；优先让现有后台结算 Agent 根据目录调用检索工具。
- 若重复痛点已经明确，再考虑将验证有效的组合封装为可选工具或作者体验改进。
- 只有现有机制确实无法满足需求，或封装能显著降低用户成本且兼容代价可控时，才重新评估专属插件/格式。
- 插件是封装方式，不代表必须由新机制取代 EJS、世界书或 MVU；保持现有卡片可继续运行是重要约束。

## 尚待验证

- 转换标记和产物版本如何记录，确保运行时能可靠区分普通卡与可检索卡。
- 精简变量目录需要哪些元数据，才能让结算 Agent 发现规则而不把目录本身变成另一份大提示词。
- 变量检索工具如何提供当前值、定义、关联规则和来源，并允许从初始检索继续扩展。
- 结算 Agent 自主检索能否覆盖候选之外的相关规则与依赖变量，并降低漏结算风险。
- 真实大卡上总 Token、检索往返次数、延迟和结算正确性如何变化。
- 在真实卡片上，工程化封装是否能切实降低卡作者和玩家的使用、排错成本。

在这些问题有实际证据前，本备忘不授权或要求实施新插件、新格式或新运行时。
