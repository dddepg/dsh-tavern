# MVU 领取请求的 HTTP 连接饥饿

Issue #88 的更正指出：自动恢复确实运行过，但任务再次领取超时。代码没有显式串行 RPC 队列，不能据此排除浏览器网络排队。

## 修复与边界

`getSession` 等视图请求使用同源 HTTP。浏览器的 HTTP/1.1 连接全部被慢请求占用时，同样使用 HTTP 的领取、开工、续租和回执无法及时送达宿主。

这些控制请求现在使用已有的 DSH Remote mux WebSocket，一次请求对应一个返回单条结果的逻辑 stream，不新增物理连接。服务端仍调用原来的调度器，只接受六种固定控制方法。结果沿用 JSON envelope，避免 Remote codec 对领取结果携带的整份脚本历史做递归校验。

传输层不自动重放、不在失败后切回拥堵的 HTTP；原执行器负责按事件标识和租约查询、重试回执。取消、会话切换、旧租约拒绝和重复回执确认沿用原契约。旧版 Remote 客户端没有控制能力时，保留原 HTTP 路径作为版本兼容。

这解决的是连接槽排队，不会让 JavaScript 在线程被同步 CPU 工作占满时继续执行。原始用户环境的全部慢请求来源没有通过本实验逐一重演。

## 验证

运行：`node tests/fixtures/runtime-control-starvation.mjs`。

此脚本使用 Chromium、已安装 DSH 的真实 mux 客户端/服务端、生成的控制契约、项目 RPC 包装和调度器。冻结六个真实 HTTP 响应，再分别尝试旧路径与新路径。

2026-09-24 本地结果：

- 六个视图请求均已抵达服务器，且保持未完成。
- 旧 HTTP 领取请求未抵达服务器；宿主以一秒测试期限产生 `claimTimedOut`。
- 新通道完成领取、开工、执行状态续租、完成回执、重复回执、心跳和释放，耗时 18 ms；六个视图请求仍未释放。
- 重复回执确认原执行，不产生第二次执行。

单元测试另覆盖控制方法白名单、JSON 兼容、取消传递、服务销毁、断线失败不重放，以及控制失败不回落到 HTTP。原有执行器测试继续覆盖会话切换、丢通知恢复和丢回执恢复。
