# Issue #89：MVU 接续唤醒与旧状态读取的竞态

来源：https://github.com/flizzywine/dsh-tavern/issues/89 。基线 `24a4880f`，已包含 #90 的读取优化。

## 确认的缺陷

自动接续机制原本存在：启动扫描、执行器就绪/任务结束通知、结算 job finally 唤醒，以及待办重试。缺口在同一 Session 的进行中检查合并逻辑：

1. 检查 A 读取的快照尚未进入 pending，例如后台操作仍处于 running。
2. A 尚未结束时，领取超时结果被持久化，任务变为 pending；执行器恢复或结算 finally 发出唤醒 B。
3. `wake()` 因 `inFlight` 已存在，直接返回 A 的 Promise，未记录 B 带来的重查要求。
4. A 根据旧快照判定无待办并退出，不安排重试。若没有后续事件，这条已保存任务可能一直等待。

该交错已通过确定性回归复现。它是 #89 现象的一个可达机制，不是报告者那次运行的唯一根因证明。进程 CPU 峰值不直接证明事件循环饥饿；没有变量写 RPC 记录，也不能区分请求排队与任务尚未开始执行。

## 修复

进行中检查收到额外唤醒时，记录每个 Session 的重查标记。当前检查结束后，使用已有重试定时器再读权威状态，多个唤醒合并为一次。生产配置仍采用 10 秒延迟，避免任务结束通知导致立即循环或增加宿主压力。

继续依赖原有接续条件、执行器就绪判断和时间线提交校验；不直接根据 pending 文案强行执行。已停止任务不会因保留的通知重新运行。没有改动 HTTP/mux 路由、领取期限、执行租约或变量事务协议。

## 验证

```sh
node --test tests/mvu-settlement-reconciler.test.mjs tests/issue89-mvu-resume.test.mjs
```

- 新单元回归：暂停旧快照读取，提交新待办并再次唤醒。旧实现没有安排重查，断言 `0 !== 1`；修复后自动接续一次。
- 集成回归：真实 Journal/Persistence、Story Timeline、Background Task Coordinator、Script Dispatch 和 Reconciler。真实 100ms 测试领取期限超时，保存 pending 回执，注入上述交错，再恢复执行器并确认领取/start/complete。变量通过时间线提交，使用另一 Store 实例读取磁盘验证。
- 浏览器脚本执行及变量效果生成由测试模拟；没有运行真实浏览器、MVU 沙箱或模型，不把它称为完整端到端验证。
- 同一交错下主动停止的任务保持停止，不提交变量；完成后的通知最多触发一次无操作复查，不重复执行。
- 临时换回未修改的协调器重跑集成测试，确认旧实现失败；随后恢复修复并验证通过。
- 包含 MVU 结算、dispatch、协调器、时间线、持久化在内的相关测试 111 项全部通过。未修改客户端，不需要重建客户端。
