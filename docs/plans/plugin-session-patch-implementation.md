# 插件内 Session 补丁实施计划

日期：2026-09-22。状态：待实施；仅记录计划，不接入生产。
实验分支：`experiment/plugin-session-patch`。依据：实验提交 `06d0c273`、[实验记录](../research/plugin-session-patch-experiment-2026-09-22.md)。

## 目标与约束

在不修改官方 DSH Desktop、DSHA、宿主 npm 文件和启动命令的前提下，由 Tavern 插件加载内存补丁，恢复正文编辑、回退和重新生成。首个目标只针对已实验的 DSH `0.1.6-alpha.2`；其他版本不自动套用补丁，也不提前声明适配。

沿用现有 Chat、timeline、变量与 Session 事务，不另做会话引擎。保留 assistant 角色、来源覆盖校验、system 首节点保护和模型请求顺序。正常生成不增加轮询、网络请求、逐 token 拦截或重复全历史扫描。

目前已证明隔离环境的核心链路可行，尚未证明真实客户端启动时序和完整产品流程可行。先解决接入时序，再投入事务完善；若必须改宿主才能安装，则停止本路线并记录阻塞，不悄悄扩大约束。

## 1. 先验证真实加载入口

交付：Desktop、DSHA 各一份加载顺序证据和最小接入原型。

- 查清 Tavern 服务加载、Session writer 打开、SessionQuery 缓存建立的先后关系。补丁必须在相关会话打开前完成；已有活动句柄时禁止强行热替换。
- 从 `tavern-plugin/lib/index.js` 接入服务器安装器；验证宿主实际解析到的包路径，而不是开发目录碰巧存在的依赖。
- 从 `tavern-plugin/src/client/main.js` 的 ModuleLoader 入口验证历史读取补丁。确认拿到实际 stream 类，并在首次订阅/历史读取之前安装；验证刷新、重连、多窗口和插件重复加载。
- 确认客户端允许加载所需模块，Android 环境支持所用编译机制；不能把 Node VM 测试视为浏览器接入成功。
- 建立一次性的客户端/服务端补丁版本握手。两端就绪前不开放编辑、回退、重生成，失败给出可操作的原因。无定时轮询。

验收：官方 Desktop 和 DSHA 均能仅通过 Tavern 加载补丁，并用隔离测试存档完成编辑、刷新和重启恢复；安装目录前后校验一致。任一平台不满足时，保留实验状态，不宣称双端适配。

## 2. 把实验脚本收敛成可维护模块

交付：服务端补丁安装器、客户端安装器、固定版本补丁清单和诊断状态。

- 服务端建议集中在 `lib/domain/host-session-patch.js`，客户端集中在 `src/client/modules/host-session-patch.js`；最终文件拆分以依赖边界为准。
- 清单记录全部相关包版本、源文件哈希、替换锚点和补丁协议版本。启动时检查一次并缓存；哈希或形状不符即停止安装，不猜测新版本兼容性。
- 分成“准备/验证”和“安装”两阶段：先编译所有模块并验证目标，后一次性替换方法。中途失败恢复已改的方法，不能留下半安装状态。
- 保持 Session、服务实例和公开错误类身份；保留原有服务资源所有权。安装幂等，重复调用不重复包装；不得覆盖其他插件后来安装的方法。
- 当前 Surface 修改是进程级的，覆盖所有 provider 的 assistant replacement。明确记录影响范围，检查同宿主普通会话回归；若能可靠识别 Tavern 所有权，再评估缩小范围，不能仅凭 provider 名过滤。
- 插件卸载/热重载必须先停止新操作、释放句柄和查询 lease。已有补丁存档不能因卸载恢复方法而继续用原版服务读写；必要时要求重启，不能制造混合运行状态。
- 诊断只记录版本、哈希、阶段、耗时和错误，不重复存储正文。

验收：成功安装、版本不匹配、编译失败、部分安装失败、重复安装和卸载均有确定行为；原有错误类型判断与服务生命周期不变。

## 3. 完善存档保护与恢复

交付：必需标记的写入规则、失败恢复测试、启用前备份与恢复说明。

- 保留 `dsh-tavern/required-session-patch-v1` 必需事件，禁止标为 ignorable。首次真实修改前写入，保证修改不能先于标记落盘。
- 先完成替换预检，再写标记；序号变化必须纳入验证，避免无效操作无故锁定存档。崩溃只留下标记时仍须能由补丁恢复。
- 启用前在暂停写入的安全点备份相关 Chat、timeline、变量和 Session；验证备份可恢复。备份可能有一次性磁盘成本，单独计量。
- 测试标记前、标记后、替换后、flush 前后以及压缩帧写入中断。未加载补丁时分别以读/写方式打开，必须拒绝且不截断、不重写文件。
- 插件能控制的入口给出明确提示。原版宿主直接打开 Zstd 的错误文案不一定可控，不承诺无补丁时也能显示友好提示。
- 停用补丁不等于转换存档：保留原存档，提供恢复到启用前备份的步骤并说明会失去备份后的进展。不做未经验证的自动去标记/降级转换。

验收：无静默退回旧正文、无丢失尾部；故障恢复后 Chat 与模型可见 Session 一致。

## 4. 接回三个完整产品操作

交付：沿用 `body-editor.js`、`round-history.js` 与既有 Surface mutation 的完整功能验证。

| 操作 | 必验行为 |
| --- | --- |
| 正文编辑 | 普通正文、多段正文、再次编辑、取消和冲突；保存后页面、Chat、timeline 与下次请求一致，变量遵守现有编辑语义 |
| 回退 | 单次/连续回退、失败回合回退、刷新与重启；变量快照、正文和原生 Session 一起回到目标状态 |
| 重新生成 | 单次/连续重生成、取消、模型失败、重启恢复；旧结果退出模型历史，新结果结算一次，既有指导语功能保留 |

同时覆盖前台/后台 Agent、文生图 Agent 的实际相关入口，检查忙碌状态与事务互斥；未覆盖的入口不得默认允许写补丁事件。验证压缩前后、长会话、导出/导入、分支/恢复以及迁移 worker 对必需标记和来源引用的处理；不支持的路径明确拦截，不能靠吞异常继续。

验收：自动回归通过，Desktop/DSHA 使用独立测试 Profile 完成真实 UI 操作；实际模型请求确认编辑生效。涉及真实模型费用的试跑另按可用测试配置执行，脚本化 adapter 结果不冒充真实服务结果。

## 5. 性能基准与控制

交付：同机、同版本、同夹具的原版/补丁对照报告，记录样本数量、冷暖启动、median/p95、RSS 与会话规模。

- 使用约 100、1,000、10,000 条事件的合法会话，并记录正文总字节数；至少 20 次暖态样本，冷启动单独统计。
- 测量启动编译/哈希、首次标记、首次/重复编辑、回退、JSONL/Zstd flush、冷恢复、历史页、订阅及本地请求构造耗时；备份成本独立列出。
- 原版不能执行的替换操作用补丁前后相同事件数的正常操作作辅助对照，另外报告补丁操作绝对耗时，不编造原版成功基线。
- 正常生成对照必须有相同模型可见输入；先用固定 adapter 排除网络噪声。比较请求前缀与服务商实际 cache usage，分别报告，不拿请求一致直接证明命中。
- 重点检查重复开关会话/刷新/重连后编译副本、句柄、缓存和监听器是否持续增长。避免每次会话创建重新编译整套模块。

初始工程预算（待测，不是已达成承诺）：暖态普通读取/请求构造 p95 增量不超过基线的 5% 或 5ms，取较大者；桌面启动增量目标不超过 300ms、稳定额外 RSS 目标不超过 20MiB。DSHA 单独测量后确定设备预算。超预算时先定位额外扫描、重复编译或缓存；不要减少正确性校验来凑指标。

验收：无每 token 开销、无轮询、正常路径无反复全历史扫描，内存不随重复操作持续增长；报告明确是否达到预算。

## 6. 收尾与发布门槛

- 每个完整功能点单独提交，实验代码与生产接入分清；继续保留原始实验作为复现证据。
- 改客户端后执行 `node bin/build-tavern-client.mjs` 和 `node bin/build-tavern-client.mjs --check`，再跑相关回归与双端 UI 验收。
- 只有完整验收后才更新 `config/dsh-compatibility.json` 的单一适配版本；Desktop/DSHA 版本以实际验收安装包为准，不由 DSH 核心版本推断。
- 发布说明明确支持版本、补丁存档依赖、备份恢复方法及已知不支持路径。首次启用使用现有页面内对话框，不能用原生 confirm/prompt。
- 本计划不授权现在发布或修改用户 Profile。先提供可审查的实验构建和验证报告，再决定正式启用/发布。
- 官方将来修复后，单独验证其能否读取这些存档及必需标记；未完成迁移前，不能直接撤掉补丁或删除标记。

执行顺序：真实入口验证 → 安装器与存档保护 → 完整事务/双端验收 → 性能基准 → 发布评审。第一步失败即可止损；暂不承诺工期，入口验证完成后再估算剩余工作。
